# Model registry

`lib/ml/registry.json` is the single record of every model that was trained and evaluated. It is generated by
`python -m ml.train.registry` and read by the API (`/api/ml/evaluation`), the forecast service, the `/models` page
and the detailed health endpoint.

## Rules

- **Append-only by `(id, version)`.** Re-registering a version whose artifact hash differs raises an error, so a
  production model can never be silently replaced; a change requires a new version.
- **Exactly one production model per task.** Enforced by a test.
- **Hash-verified.** A test recomputes the SHA-256 of the production artifact and compares it with the registry.
- **Rejected models stay on record** with the gate checks they failed and no artifact.
- **The serving code refuses** an artifact that is not the registered production version
  (`buildRiskForecast` throws if `VOL_ARTIFACT` is not the production entry).

## Fields

| Field | Meaning |
|---|---|
| `id`, `version`, `task`, `status` | identity and lifecycle (`production`, `superseded`, `rejected`) |
| `artifact`, `artifactSha256` | JSON artifact path and hash (null for rejected models) |
| `trainedAt`, `featureVersion`, `datasetSha256` | provenance: when, which feature code, which exact dataset file |
| `fitRange`, `calibRange`, `hyperparameters` | what data the artifact was fit and calibrated on |
| `validation` | walk-forward method, range and metrics |
| `holdout` | holdout range, metrics and `pristine` flag |
| `gate`, `reason` | pre-registered checks and the failure reason (rejected models) |
| `limitations` | shown to users on the model card |

## Production artifact (`lib/ml/artifacts/volatility-ridge-1.1.0.json`)

Contains the ordered design columns, winsorisation bounds, standardisation means and scales, coefficients, intercept,
and the residual quantiles used for the 80% interval. TypeScript inference (`lib/ml/volatility.ts`) applies exactly
these, verified against Python on 25 real rows to 1e-6.

The production artifact was refit on all labelled data (fit 2011-01-03 to 2025-09-23, calibration
2025-10-01 to 2026-10-01) with the same procedure and hyper-parameters. The reported holdout metrics belong to the
pre-holdout fit; the refit has no separate out-of-sample score yet.

## Promoting a new model

1. Change the code, bump `VERSION` in `ml/train/final_vol.py`.
2. Run the walk-forward study; the pre-registered rule chooses the model.
3. Score the holdout once (a new holdout period is needed for a pristine result).
4. Export, regenerate parity fixtures, `python -m ml.train.registry`, mark the old version `superseded`.
5. Point `lib/ml/volatility.ts` at the new artifact; the hash, parity and single-production tests must pass.
